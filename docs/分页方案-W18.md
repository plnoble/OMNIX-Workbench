# 分页方案（W18）

> 状态：**已设计，未实施**。2026-08-19 定稿。
> 触发点：单会话消息 > 500 条，或会话数 > 200 个。到了再做。

第二份技术审查的 W18「对话 / 消息无分页」。审查报告的建议是「否（先加上限保护，
完整分页下一迭代）」，但**只加上限是错的那一半**——报告自己也写了「不要在没做 UI
的情况下把列表静默截断成很小的数」：用户会以为历史丢了，比慢更糟。

所以要么连 UI 一起做，要么先不做。这份文件是「连 UI 一起做」的方案。

## 一、为什么现在不做

2026-08-19 实测本机库：

| | |
|---|---|
| 会话 | 2 个 |
| 消息 | 20 条 |
| 单会话最多 | 18 条 |
| 正文合计 | 0 MB |

现在做分页是给一个不存在的问题上机器。**触发点**：单会话 > 500 条，或会话 > 200 个。

## 二、摸出来的三件事（它们决定了方案的形状）

### ① 真正的热点不是缺 LIMIT，是「每个事件重拉全量」

`src/hooks/useConversations.ts` 里，收到 `assistant_message` / `plan` /
`tool_completed` 事件时会把**整个会话的消息重新拉一遍并整体替换**
（`const persisted = await conversationApi.getMessages(...); setMessages(persisted)`）。

一轮对话有几十个这样的事件。18 条消息时无所谓；5000 条时是**每个事件一次全量读 +
全量重渲染**。

**而且先加分页会让它更糟**：重拉会把用户翻上去加载的历史窗口冲掉。所以这一步必须
排在分页前面。

### ② 索引不支持排序，LIMIT 加了也不便宜

```
SELECT ... FROM messages WHERE conversation_id = ? ORDER BY timestamp ASC
  -> SEARCH messages USING INDEX idx_messages_conversation_id (conversation_id=?)
  -> USE TEMP B-TREE FOR ORDER BY          ← 每次都排一遍整个会话

SELECT ... FROM conversations WHERE COALESCE(is_archived,0)=0 ORDER BY created_at DESC
  -> SCAN conversations                     ← 全表扫
  -> USE TEMP B-TREE FOR ORDER BY
```

只有 `messages(conversation_id)` 单列索引。没有 `(conversation_id, timestamp)`，
SQLite 仍要把该会话全部消息排完序才能取前 N 条——LIMIT 省的只是传输，不是扫描。

`conversations` 上 `COALESCE(is_archived, 0) = 0` 这个写法**索引用不上**：条件列被
函数包住就不可 sarg。

### ③ 改动面意外地小

前端对 `messages` 数组只有一处 `.map()` 渲染，没有任何 `.length` / `.find` /
`.filter` 依赖。压缩（`compact_core`）、导出、备份全在后端读全量，不受影响。
**没有隐藏的「假设全量在手」的功能**——这是分页可行的前提，先确认过才有这份方案。

## 三、四个阶段

### 阶段 0 · 索引（无 UI，独立有价值，风险最低）

```sql
CREATE INDEX idx_messages_conversation_timestamp
  ON messages(conversation_id, timestamp);          -- 消掉 TEMP B-TREE

-- is_archived 规范成 NOT NULL DEFAULT 0 并回填，然后：
CREATE INDEX idx_conversations_archived_created
  ON conversations(is_archived, created_at DESC);   -- 去掉 SCAN
```

第二条要改列约束 + 回填，走 `db_schema.rs` 的迁移清单。**注意那里有两批 ALTER，
加列前先确认目标表的 CREATE 排在哪一批**（这个坑记过账）。

同时把查询里的 `COALESCE(is_archived, 0) = ?` 改成 `is_archived = ?`，否则新索引
仍然用不上。

**这一阶段现在就可以做**：它让当前查询也变快，不碰任何契约。

### 阶段 1 · 消掉「每事件重拉全量」（分页的前置条件）

事件载荷（`RuntimeEvent`）只有 `kind` / `text` / `item_id` / `metadata`，
**没有持久化后的消息 id 与 timestamp**——这正是它只能重拉全量的原因。

加一条命令：

```rust
get_messages_since(conversation_id, after_timestamp, after_id) -> Vec<MessageInfo>
```

前端记住当前窗口最后一条的 `(timestamp, id)`，每个事件只拉新增的那几条追加。

**这一步单独就能把长会话的卡顿治掉大半，且不需要任何 UI 改动。**

### 阶段 2 · 消息分页（后端 + UI）

后端：

```rust
get_conversation_messages(conversation_id, before: Option<Cursor>, limit: u32)
```

游标用 **`(timestamp, id)` 复合**，**不用 OFFSET**——对话在翻页期间会插入新消息，
OFFSET 会错位和重复。

UI 契约（这部分是「不能静默截断」的落点）：

| 元素 | 行为 |
|---|---|
| 初次加载 | 最近 **60 条**（chat 语义是从最新往回，不是从最早） |
| 顶部固定条 | **「上面还有 1,240 条 · 加载更早 60 条」**——剩余数必须显示 |
| 滚到顶 | 自动触发**一次**；不做无限自动，否则用户想看的位置会被冲走 |
| 滚动位置 | 加载前记 `scrollHeight`，加载后 `scrollTop += 高度差`；不补偿视野会跳 |
| 回到最新 | 不在底部时显示浮动按钮 |
| 跳转命中 | 搜索 / 引用跳到历史某条时，以该条为中心加载前后各 30 条 |

剩余数需要一个 `COUNT(*)`，有了阶段 0 的索引它是覆盖索引查询，可接受。

### 阶段 3 · 会话列表（**不做无限滚动**）

`src/components/layout/AppSidebar.tsx` 是**按 agent 分组**遍历全部会话的。分页会
直接打断分组语义：翻到第二页可能整组消失。

所以改成 **「最近 100 + 搜索」**：

- 默认取最近 100 个；
- 搜索走**后端 SQL**（标题 LIKE 或接 FTS），不是前端过滤——前端过滤需要全量在手，
  等于没分页；
- 侧栏底部写明「显示最近 100 个会话 · 搜索全部」；
- **归档视图本来就是独立页面，建议先拿它试水**，风险更低。

## 四、不做

**虚拟化**（react-window 之类）。那是渲染层，和分页是两件事；60 条 DOM 不需要它。
等真出现「一屏内 1000+ 节点」再说——而分页本身就避免了这种情况。

## 五、验证方式

- 阶段 0 / 1：`EXPLAIN QUERY PLAN` 不再出现 `TEMP B-TREE` / `SCAN`；造一个 5000 条
  消息的会话，量「一轮对话期间的查询次数」从 O(事件数 × 全量) 降到 O(事件数 × 新增)。
- 阶段 2 / 3 的反向验证：**把「上面还有 X 条」那行删掉，必须有测试变红**。静默截断
  正是这条要防的东西，守不住它就等于没做 UI。
