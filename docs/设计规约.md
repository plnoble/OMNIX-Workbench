# 设计规约

两条**判断**，不是命令。写下来是因为它们只在写代码的当下生效——事后看 diff
是看不出来「本来不该加这个」的。

2026-08-21 借鉴自 [cumora](https://github.com/yetone/cumora)（MIT）的
`docs/COORDINATION.md`，那是一份本机并发拉起 agent CLI 的踩坑复盘。

> 放在这里而不是只放 CLAUDE.md：那个文件是 gitignored 的（OMNIX 会往里写本机
> 个人记忆），换台机器或重新 clone 就没了。CLAUDE.md 里只留一句指向这里。

## 规约 1：提示词只写形状级规则，不堆场景化例子

**危险模式**：看到 agent 在某个具体场景做错，就往 system prompt 里加一条
「如果是 X 任务，就……」的针对性说明。

**为什么不行**：

1. 撑大提示词，占掉本该给核心规则的注意力；
2. **让 agent 在别的形状上变差**——写死了「计数任务怎么办」，它反而认不出
   接龙、投票是同一个形状；
3. 开启「每观察到一个 bug 就加一条」的滑坡。cumora 把这个叫「最贵的一类提示词 bug」。

**正确做法**：先问两句。

- 现有的形状级规则是不是**已经覆盖**了、只是没被遵守？
  是的话，把原规则改清楚，比新增一条强。
- 这是不是**提示词修不了的竞态**？是的话该上代码机制，加规则没用。

**反过来同样成立**：大脑明明看着正确的状态还做错决定，那是判断问题，别用代码
机制去堵——堵不住，只会多一套要维护的东西。

**本项目的相关位置**：`skill_library.rs`（技能注入）、`memory_recall.rs`（记忆召回）、
`commands/team_runtime.rs`（团队 worker 提示词）。

## 规约 2：已经有防护机制了，就别再加第二个

**危险模式**：系统里已有 N 个机制在防同一类问题，又为某个新观察到的现象加第 N+1 个。

**正确做法**：**先找出现有 N 个里哪一个本该抓住却没抓住，修那一个。**

**本项目的实例**：「只写不读的表」守卫（`tests.rs::table_wiring`）失效过两次——
`DELETE FROM x` 被当成读 x，注释里的 SQL 也被当成读。两次的正确修法都是**修那道
守卫本身**，而不是再加一道新的。

这和本项目一直在用的「合并不加法」是同一句话，只是说得更具体：加机制之前，
先证明现有的那些确实都不适用。
