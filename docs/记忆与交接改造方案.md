# 记忆与交接改造方案

**状态：三阶段全部实施完毕**（2026-08-22 立，同日修订并实施完成）。实施记录见文末。

## 来由

对照两个项目得出：

- [ai-memory](https://github.com/akitaonrails/ai-memory)（**MIT**，Rust）——
  解决的正是 OMNIX 的问题：「跨 agent 厂商的长期记忆与交接」。同语言同许可，
  思想和代码都能借。
- [OpenViking](https://github.com/volcengine/OpenViking)（**AGPL-3.0**，Python）——
  ⚠️ 只能 clean-room 看思想，**一行代码都不能抄**（OMNIX 是 MIT 且公开，会被传染）。
  它的主张是把 Memory / Knowledge RAG / Skills 统一进一个命名空间。

对照过程中已经查出并修掉一个真 bug（长对话交接丢的是**最新**几轮而不是最老的，
见提交 `3eae48a`）。本方案是那之后剩下的部分。

## 现状测量

不是印象，是查出来的数字：

| 项目 | 现状 | 位置 |
|---|---|---|
| 交接内容 | 最近 24 轮**原文摘录**，单条 1200 字上限，整体 8000 字预算 | `runtime.rs` `format_recent_transcript_lines` |
| 技能注入 | 匹配 top-5，网关只注前 2 条，**单条 6000 字上限** → 每请求最多 12000 字 | `skill_library.rs:247`、`proxy_anthropic.rs:68` |
| 记忆注入 | top-3 条 | `memory_recall.rs:254` |
| 内部模型调用 | loopback POST `/v1/chat/completions` + `x-omnix-model` 头 | `knowledge.rs:1218`（可直接照抄的样板） |
| 检索排序 | **三套各写各的**，只共享 `segment_for_index` 一个分词器 | `knowledge.rs`(BM25+向量+RRF) / `memory_recall.rs` / `skill_library.rs` |

最后一行是 OpenViking 那条主张的现实照应：三套独立实现的代价已经付过——
同一个中文分词 bug 在三处**各自独立复现**过一次（记忆库 `cjk-tokenization-half-migrated`）。

## 阶段 1：交接改成摘要（推荐先做）

**问题.** 交接给接手 agent 的是原文摘录。两个毛病：8000 字预算在长对话里必然
截断（截断方向刚修对，但截断本身还在）；原文里大量细节是接手方不需要的，而它
真正需要的「还有什么没解决、下一步该干什么」反而要自己从原文里推。

ai-memory 给的是**摘要 + 开放问题 + 下一步**。

**做法.**

1. `build_conversation_handoff_context` 增加一条摘要路径，走既有的内部模型调用
   （照 `knowledge.rs:1218` 的样板：loopback + `x-omnix-model`）。
2. **可选降级是硬要求**：模型不可用 / 超时 / 返回空 → 退回现有的原文摘录路径。
   那条路现在是对的，留着当兜底。超时设短（20 秒量级，不是 knowledge 那边的 180），
   宁可降级也不让用户干等。
3. 缓存键 `(conversation_id, 最后一条消息 id)`。同一会话反复交接不重算；会话
   推进一条就失效。
4. 提示词按 `docs/设计规约.md` 规约 1 写成**形状级**：三段（已完成什么 /
   未解决的开放问题 / 建议的下一步），**不给场景例子**。

**判据（测试）.**

- 假上游返回摘要 → 交接块里是摘要，不是原文。
- 假上游 500 / 超时 → 交接块**仍然存在**且是原文摘录。降级不能变成静默丢失。
- 同一会话连续两次交接 → 只打一次上游。
- 会话推进一条消息后再交接 → 重新打（缓存键含最后消息 id）。

**风险.** 交接时多一次模型往返。缓解见上面第 2 条。

**工作量.** 中。一个函数 + 缓存 + 4 条请求级测试。

## 阶段 2：抽出共用的文本相关性

**问题.** 三套检索各写各的排序。`knowledge.rs` 那套（BM25 + 向量 + RRF）明显更好，
另两套是朴素的 `contains` 计数。共享的只有分词器——于是分词修好了，排序仍然各是各的。

**做法.** **不是**把三者统一进一个命名空间（那是 OpenViking 的做法，对单机桌面
太重）。只抽出真正重复的那一层：

- 抽一个 `text_relevance(query, candidates) -> scores`，三处共用。
- **各自的领域权重留在各自那边**，叠在共用分数之上：记忆的工作区/置信度/重复次数、
  技能的类别加成。这些本来就该不同，不该被合并。

这是「合并重复的部分，不合并本来就该不同的部分」——`docs/设计规约.md` 规约 2 的直接应用。

**判据.**

- 一份共享语料，三处的**基础相关性**排序一致。
- 各自的领域权重仍然生效。反向验证要能分离：去掉工作区加权 → 记忆那条红、
  技能那条不动。

**风险.** 低。纯重构，既有测试兜底。

**工作量.** 中。

## 阶段 3：让截断的技能可恢复（**已改小，原方案作废**）

> 2026-08-22 修订。原方案是「加 `abstract` 列 + 加 `skill_read` MCP 工具」。
> 读 [hallmark](https://github.com/Nutlope/hallmark)（MIT，26.7k star）之后作废了：
> **这两样机制 OMNIX 都已经有了或者不需要**——正是设计规约 2 说的那种情况。

**问题（比原先估的严重）.** 注入是**正文原样塞入**，单条封顶 6000 字，超了就截断
并留一句「已截断」——但**注入块里不给技能所在路径**（只有 `## Skill: {名字}` + 正文）。
于是截断是**死路**：模型拿到半份技能，没有任何办法读到剩下的。

拿 hallmark 实测：它的 `SKILL.md` 是 **67 KB**，到 OMNIX 这里只剩 **9%**。更糟的是
它整个设计就是靠正文里的 `references/*.md` 链接做渐进披露，而那些链接在第 6000 字
之后——模型连「还有参考文件」这件事都不知道。26.7k star 的技能不是异类，那就是
成熟技能的样子。

**OMNIX 已经有的两半，只差没接上：**

1. `{name}_core.md` 约定**早就在**（`skill_pool.rs` / `skill_sync.rs` / `safety.rs` /
   `commands/skills.rs` 五处在用），注入时优先读它、读不到才退回 `SKILL.md`。
   这就是 L0/L1 里的 L0，不需要新加 `abstract` 列。
2. agent 本来就有读文件的能力。hallmark 的做法是 `SKILL.md` 里直接写
   `references/xxx.md` 相对链接，agent 用**普通的读文件工具**取——不需要专门的
   `skill_read` MCP 工具。

**做法（小得多）.**

1. 注入块的每条技能标头带上**技能目录的绝对路径**。
2. 截断时那句提示改成可操作的：「已截断，完整内容在 `<路径>/SKILL.md`」。
3. 就这些。不加列、不加工具、不改 schema。

**判据.**

- 超长技能的注入块里含有其目录路径（反向验证：去掉路径 → 该条红）。
- 未截断的技能行为不变（证明改动只影响截断那条路）。
- 路径来自「`central_path` 非空时优先、否则 `file_path`」——和读取端用同一个表达式，
  免得注入说的路径和实际读的位置对不上。

**风险.** 技能存在中央库里，路径通常在工作区**之外**——agent 读它可能触发权限询问。
这是真实摩擦，但不是阻塞：至少从「无解」变成了「点一下允许」。要不要把中央库路径
加进默认允许列表，是另一个决定，不在本阶段。

**工作量.** 小。约十行 + 三条测试。

**顺带记一笔**：可以把 hallmark 本身收进正式技能池（MIT，可直接用）。OMNIX 的
幻灯渲染器 `slides.rs` 产出 HTML，正是它的适用面。但那是内容工作，不属于本方案。

## 明确不做，及理由

| 不做 | 理由 |
|---|---|
| OpenViking 的 `viking://` 虚拟文件系统（`ls`/`tree`/`find`） | 对单机桌面是重型基础设施。它要解决的「让检索轨迹可观察」在 OMNIX 这个体量上用日志就够。 |
| git 版本化的 markdown wiki（ai-memory 的 `checkpoints` / `restore-page`） | 时间旅行能力确实好，但「记忆改错了想回滚」这个痛**在本项目没发生过**。等它发生再做。 |
| ai-memory 的 15 家 CLI 适配矩阵 | OMNIX 是工作台，不是记忆中间件。适配面不是它的价值所在。 |
| OpenViking 的自进化异步抽取 | OMNIX 的蒸馏是**用户显式发起**的，那是有意的设计（见 `omnix-is-supervisor-not-executor`）。 |

## 顺序

**3 → 1 → 2**（原为 1 → 2 → 3，阶段 3 改小之后重排）。

- 阶段 3 现在是三者里**最小**的一个（约十行），而且修的是一条**死路**——
  超长技能当前无解。先拿掉。
- 阶段 1 收益明确、风险中等（多一次模型往返，有降级兜底）。
- 阶段 2 是纯重构，收益是防未来的 bug 而不是修现有的，放最后。

三个阶段互相独立，任何一个都可以单独停在那里，不留半套。
